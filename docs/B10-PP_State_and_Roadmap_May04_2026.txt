SECTION 3 — DO NOT REOPEN THESE DECISIONS
════════════════════════════════════════════════════════════════════════

These are locked. Do not revisit without explicit instruction from J. Moore.

ILR target values: "2" and "3" only. No "2+" anywhere in schema.
Score field ESO: integer 1–4. LEVEL2: integer 1–3. Not ILR levels.
ILR labels in student feedback: Out of scope. Never.
corpusType "CC": It is "COR". Do not reintroduce "CC".
Track on /students: immutable after creation. trackOverrideNote required for override.
PSU as scaffold axis: Not selectable. Always implicit. argument_structure foregrounds it.
MF vocab in scaffold system: Not included. Phase 4 evaluation layer only.
Auto-generated note summary: On-demand only. Never on note write.
EXT as umbrella: EXT is a subtype. One canonized long-form family.
STT Pass 1: Deepgram (disfluency preserved). NOT Whisper. NOT AssemblyAI.
STT Pass 2: AssemblyAI (conditional, instructor-facing only). NOT scoring engine input.
Scoring engine: Claude Sonnet, temperature = 0. Non-negotiable.
Raw transcript: NEVER smoothed before reaching scoring engine.
submissionNumber: Server-side transaction only. Client always writes 0.
Score 1 + Pass 2: Permanently incompatible. Hard block in code.

Auth method: Email/password only. Anonymous and phone auth ruled out.
Entry flow (Option C): Access code only on EntryScreen. b10Id always
  comes from custom claims — never from user input. Student never types
  their own ID.
b10Id is a backend pseudonym: Students never see or type it. Instructors
  use it as a lookup key. Like a medical record number — internal only.
b10Id format: {accessCode}-{sequence} e.g. 26-001-1, 26-001-2, 26-001-15
  Access code uses leading zeros (26-001) for sort/readability.
  Student sequence number has no leading zeros (1, 2, 15, not 001).
Access code format: YY-NNN (e.g., 26-001, 26-002)
  System auto-increments per year. Up to 999 codes per year.
  Single code — instructor distributes, student types directly.
  No separate PIN layer (revisit only if scaling requires it).
Default enrollment track/baseline: track "B", ilrBaseline "3".
  Instructor changes individually if needed after enrollment.
Instructor student lookup: Two paths — (1) by name/email for discovery,
  (2) by b10Id for fast instructor-to-instructor hand-off (e.g. SLT teacher).
  Both paths return the same student record view. Build in Week 4 dashboard.
Role authority: Custom claims are the single source of truth for role.
  The /users collection is NOT used for role checks anywhere.
Instructor provisioning: Admin (J. Moore) creates instructor Firebase Auth
  accounts manually and sets claims via setStudentClaims or setAdminClaims
  script. Instructors never self-register.
Scoring rubrics: DO NOT MODIFY without Director approval. Hard-won over
  1.5–2 weeks of iteration. Any grammar/quality fix goes through the
  post-generation validation layer (see Section 3B), not the rubrics.

SECTION 7 — STRATEGIC VISION (POST-PILOT ROADMAP)
════════════════════════════════════════════════════════════════════════

These are confirmed strategic directions, not current build items.
Capture here so they are not lost. Sequence TBD after pilot data exists.

ITEM 1: Two-tier feedback system
  Current: Rating feedback only (concise, score-anchored, immediate)
  Future: On-demand extended feedback button on FeedbackScreen
    - Student taps "Get detailed feedback" after seeing score
    - Second Claude call with different prompt — warmer tone, specific
      language examples, encouragement framing, actionable suggestions
    - Not a re-score — deeper read of same transcript
    - Implemented as new callable (requestDetailedFeedback), similar to
      requestPass2 architecture
    - Addresses student discouragement at lower score bands
    - Strategic value: separates "machine rated me" from "machine helps me"
      — stronger instructor buy-in argument
  Schedule: After pilot baseline established. Pre-S3 argument.

ITEM 2: Post-generation grammar validation layer (ISSUE-6 — pre-pilot)
  During supervisor demo, feedback text contained minor grammatical errors.
  Cannot touch scoring rubrics (too risky). Solution: additive validation pass.
  Architecture: After Step 10 (Claude scoring), before Step 12 (write results),
    a second lightweight Claude call reviews strengths, gaps, language_feedback
    for grammatical errors and corrects them before Firestore write.
  Prompt: "Review these feedback strings for grammatical errors. Correct
    any errors. Return corrected versions in same JSON structure. Do not
    change meaning or tone."
  Adds ~2-3 seconds latency. Acceptable for formative tool.
  Rubrics untouched — zero scoring risk.
  Schedule: Week 3 or Week 4 — pre-pilot required.

ITEM 3: AESOP-B10 independent practice sequence
  Concept: A standalone 8-week discourse frame learning sequence built
    entirely inside B10-PP, mapping directly onto the AESOP course structure.
  Structure:
    - 8 weeks × 5 days = 40 lesson nodes
    - Each node has a reasoning target (e.g., W3-D2 = causal chain extension)
    - Each node maps to specific B10 task types (paraphrase, ESO, counter,
      hypothetical)
    - Each node has its own MF vocabulary cluster and grammar focus
    - Intro video per week frames the discourse target before practice
    - Students work through independently — no instructor required for practice
  Strategic value:
    - Does not depend on curriculum adoption — builds regardless
    - Gives B10-PP a complete pedagogical backbone beyond "practice tool"
    - Strongest possible S3 argument — not just a tool, a full instructional
      sequence with measurable ILR 2+ → 3 outcomes
    - Pilot data feeds directly into the adoption argument
  Discourse frames: W1 Scale/Stakeholders → W2 Trade-offs → W3 Causal Systems
    → W4 Hypothetical → W5 Values/Bias → W6 Synthesis/Judgment →
    W7 Systems Description → W8 Integrated Multi-Frame
