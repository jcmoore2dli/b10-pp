## 4. Deploy Procedure (corrected — read this before deploying)

**Don't deploy manually. Never improvise a `cp` command.** Use the existing script:

```bash
cd frontend && npm run deploy
```

This single command builds the app, copies the output into the correct nested path (`hosting/b10_practice_platform/`, matching the app's Vite `base` config), and runs `firebase deploy --only hosting`. It now also creates the destination folder automatically if it's missing, so it can't fail silently partway through the way it did the first time this was discovered.

**Always verify after deploying — don't trust "Deploy complete!" alone.** Check the actual JS asset URL, not just the homepage:

```bash
curl -sI https://b10-practice-platform.web.app/b10_practice_platform/assets/[bundle-hash].js
```

(Get `[bundle-hash]` from the `dist/assets/index-XXXXXXXX.js` line that `npm run build` prints.) Look for `HTTP/2 200` and `content-type: text/javascript`. A `404` or `text/html` here means the deploy is genuinely broken even if the deploy command itself reported success with no errors.

### Why this matters

When this breaks, the symptom is a completely blank white screen on the live site — but *only* on a genuinely fresh load with zero existing cache or service worker history for the site. Any browser tab, device, or window that visited the site before the break can keep working fine indefinitely afterward, because a previously-cached working bundle keeps getting served locally even while the live deploy is broken for every new visitor. This is what makes the bug dangerous: it can hide behind your own browser's cache for an entire session of "successful" testing while being completely broken for anyone hitting the site fresh.

### Diagnostic technique worth remembering

If a deploy reports success but something seems off, don't trust testing in an already-used browser tab — even after clearing cache, since clearing cache doesn't always remove an installed PWA's separate storage container or a stuck service worker. The reliable test is a brand-new private/incognito window, or better, a device or browser that has genuinely never visited the URL before. If that *also* fails, the problem is real and server-side, not local caching — go look at the actual response headers and content-type for the specific asset files, not just the HTML page.

### The specific historical bug (for context, already fixed)

Vite's `base: '/b10_practice_platform/'` config makes every asset reference in the built HTML point to `/b10_practice_platform/assets/...`, but Vite's physical build output still places files at `dist/assets/...` (not nested). A flat `cp -r dist/* hosting/` therefore puts files at `hosting/assets/...`, which doesn't match the URL path the browser actually requests, so Firebase Hosting returns a 404 (or its own HTML error page) for every JS/CSS asset — while the homepage HTML itself still loads fine, masking the problem from anyone testing only the index page. The existing `npm run deploy` script already handles this correctly by copying into the nested `hosting/b10_practice_platform/` path; the only failure mode was the destination folder not existing yet, which is now handled automatically.

## 5. Git Workflow Conventions Observed in This Project

- **Feature branches** for any new, substantial piece of work (e.g. `feature/flexibility-scaffold-standalone`, `feature/core-bundle-progress-display`).
- **Integration branches** when combining multiple feature branches before merging to `main` (e.g. `integration/flexibility-test`), so testing happens before `main` is touched.
- **Commit early, commit often** — don't wait for a feature to feel "done" before committing. A work-in-progress commit on its own branch costs nothing and protects against losing work if a session ends abruptly. (This project has lost track of uncommitted work across home/work machines before — see the CORE bundle progress display recovery below.)
- **Always verify before merging into `main`** — mechanical checks (does the code reference the right thing) are not sufficient on their own; trace whether the *consuming* logic actually reads the new value too. This project has repeatedly hit bugs where a new value was added to a data model in one place but a separate consumer (Firestore rules, a derivation function, a UI badge switch, a guide-link lookup) was never updated to recognize it. When adding a new categorical value anywhere in this codebase, grep for every existing case of the *similar* values it's joining, and check each one.

### Worked example: recovering uncommitted work across two machines (June 17, 2026)

A home computer had real, substantial uncommitted changes to `InstructorDashboardScreen.jsx` (a CORE bundle progress display feature) that had never been committed or pushed, discovered only when a `git pull` was blocked by a merge conflict. Recovery sequence used successfully:

```bash
# 0. Independent backup outside git, just in case
cp frontend/src/screens/InstructorDashboardScreen.jsx ~/BACKUP_$(date +%Y%m%d_%H%M).jsx

# 1. Stash the local changes safely
git stash push -m "WIP: description of the work"

# 2. Pull the remote changes now that the conflict is out of the way
git pull origin main

# 3. Create a branch for the WIP work rather than letting it land on main
git checkout -b feature/descriptive-name

# 4. Reapply the stashed changes onto this new branch
git stash pop
# (git can often auto-merge two independent sets of changes to the same file
#  cleanly; if it reports a conflict instead, stop and resolve it carefully
#  rather than guessing — the backup from step 0 means nothing is at risk.)

# 5. Commit and push immediately so the work is durable
git add <file>
git commit -m "WIP: description"
git push -u origin feature/descriptive-name
```

## 6. Quick-Start Checklist for a New Session

1. `cd ~/b10_corpus/b10_practice_platform && git pull origin main`
2. If continuing frontend work: `cd frontend && npm run dev` (or `npm run preview` to test an actual production build locally before deploying).
3. Before any Cloud Function changes: view current `functions/index.js` and `functions/lib/claudeScorer.js`.
4. When deploying: `cd frontend && npm run deploy`, then verify with the `curl -sI` asset check in Section 4 — every time, no exceptions.
5. Commit and push before ending the session, even if a feature isn't finished — see Section 5.
